# 可抄的做法：只跑受影響的突變＋每條突變的帳本＋資源紀錄（MealMate，2026-10-02）

> 給 JLPT_App、StockDiary、TripQuest 照抄用（Dispatch 2026-10-02 指示：MealMate 先做，做完寫成可抄的說明）。
> 對應共用慣例 v11 §5.18（只跑受影響的、帳本）、§5.19（資源上限與紀錄）、§5.20（機制要真的被執行過）。
> **狀態**：程式寫完、輕量的部分實測過；doctest 與突變（重負載）還沒在 Dispatch 排的時段跑——照抄之前先看本 App STATUS「共用慣例副本更新到 v11」一節的待跑清單有沒有跑完、有沒有改動。
> 原始碼：`scripts/depgraph.mjs`（範圍、雜湊、帳本的純函式）、`scripts/mutationtest.mjs`（執行器）、`scripts/sincefull.mjs`（列從沒全跑過的）、`scripts/reslog.mjs`（資源紀錄）、`scripts/doctest.mjs` 的「受影響 D1–D25」「資源紀錄 R1–R3」兩節（對照組）。

## 一、核心想法：每條突變記三個雜湊，三個都沒變就沿用

一條突變的結果只由三樣東西決定：**突變本身**（改哪個檔、找什麼、換成什麼、由哪支測試驗、expect、那支測試的逾時）、**那支測試執行時讀到的每一個檔**、**執行器**（突變執行器與它 import 的共用工具）。三樣都沒變，重跑的結果一定一樣。

所以不是「這次改了哪些檔 → 推出哪些突變受影響」，而是**每條突變自己算一個依賴範圍，把範圍裡每個檔的內容雜湊起來**；跟帳本裡上次的雜湊比，變了就跑。好處：

- 不用維護「改到 X 要跑 Y」的對照表（MealMate 2026-09-19 就是因為人工對照表漏掉一次才刪的）。
- 中斷、換 commit、分段都不影響判斷——比的是內容，不是時間或 commit。
- 「續跑」與「受影響」是同一套：整套中斷後再下一次，已經在這個 commit 上算數地跑過、雜湊沒變的自動跳過。

**要不要跑**（`rerunReasons`，任何一項成立就跑）：從沒跑過｜突變本身改了｜範圍裡有檔案改了｜執行器改了｜上次不算數（逾時、被殺、沒跑起來）｜上次沒紅｜上次沒記雜湊（從舊名單轉入的）。

## 二、依賴範圍怎麼算（一律從寬）

1. **照 import 遞迴**：從測試檔與突變的目標檔出發。認四種寫法：`import … from '…'`（**含跨行**，regex 用 `[^;]*?` 跨行）、`import '…'`、`export … from '…'`、`import('字面')`。bare 套件名不算檔案依賴（由 lock 檔管）。
2. **一律算進每一條**：資料目錄、`package.json`、`package-lock.json`。
3. **判斷不出範圍 → 整個 repo**：範圍裡任何一支程式有讀檔或跑別的程式（`readFileSync`、`readdirSync`、`existsSync`、`statSync`、`execFileSync`、`spawnSync`、`fetch`、`Worker`…），而路徑**不是** `path.join(ROOT, '字面', …)` 這種寫死的形狀；或 `import(` 接的不是字面。寫死路徑的：只把那個檔（或那個資料夾底下）算進來。
4. **讀不到不是沒有關係**：import 指到 repo 裡沒有的檔、讀不出內容 → 整個 repo（§5.13）。這是統籌者在 StockDiary 讀到的疑點，MealMate 第一版也中了（`has(target)` 不成立就默默跳過）。
5. **未知類別 → 算進每一條**：寫一張「已知類別」登記表（`KNOWN_CATEGORIES`：哪個資料夾、哪個檔，各自怎麼進範圍）；**不在表上的檔算進每一條突變的範圍**，它一改就等於全跑。登記制，不是排除制。
6. **瀏覽器測試**（範圍裡用到 puppeteer）：看不出畫面載了什麼 → 「整個 App」。App 自己的程式裡寫不死的 `fetch`、`import(`（例如 store 的資料載入、router 的動態載入）也算「整個 App」，不必退回整個 repo——App 只會載 App 的檔。
7. **「整個 App」排除文件目錄的前提要有東西守**：MealMate 讓測試用的靜態伺服器 `serve.mjs` **一律不送 `docs/`**（doctest 起一個真的伺服器去要，必須 404），而且文件目錄裡出現可以被 import 的檔（`.js`、`.json`…）就退回整個 repo。一開始用「掃 App 程式有沒有 `docs/` 字串」來守，被資料檔裡的出處欄位誤判，才改成這兩道結構上的保證。
8. **帳本檔本身不算進任何範圍**，不然每寫一次帳本，全部都變成「改過了」。
9. **執行器的雜湊**：突變執行器的原始碼**拿掉突變清單那一段**再雜湊（不然每加一條突變，全部都變成「執行器改了」）＋它 import 的每一支。找不到清單的頭尾、import 不到的檔 → 停，不默默少算。

### 照抄時會踩到的坑（MealMate 實際踩過的）

- **註解裡的字也會被當成 import**：`depgraph.mjs` 自己的註解寫了一段動態載入的範例，被當成一行真的 import、指到不存在的檔。範例改用文字描述。
- **瀏覽器測試在 `page.evaluate` 裡寫的動態載入**是在頁面裡執行的，從測試檔的位置解析一定落空 → 第 4 點會把每支瀏覽器測試都退回整個 repo。處理：落空的位置如果在「整個 App」範圍內（不在文件目錄），視為已涵蓋。
- **共用的讀檔工具會把一大群拉進整個 repo**：MealMate 的 `build-recipes.mjs` 讀檔路徑是參數，202 條突變因此是整個 repo，改 `docs/STATUS.md` 也要重跑。v11 規定手寫規則「只准讓範圍變大」，所以**不加「人工宣告它只讀資料目錄」的例外**；要縮只能改寫那支工具。
- **舊的探針預設跑法變了**：把預設從「整套」改成「受影響」之後，doctest 裡驗「整套跑完才寫基準清單」的探針要明講 `--full`，不然它驗的東西就默默變了。
- **`expect` 不能用迴圈組出來的標籤**：`expect` 要在測試原始碼裡找得到字面（§5.9），`受影響 D24${k}` 這種寫法找不到 → 標籤寫成字面陣列。
- **新標籤先搜一次有沒有撞名**：MealMate 新加的 D1–D6 跟 doctest 既有的 D1–D6 撞名，`expect` 可能紅錯地方 → 全部加前綴「受影響 D…」。
- **突變的 `find` 指向執行器自己時要帶換行**：突變清單本身就在執行器檔裡，`find` 字串會在清單的字面裡再出現一次 → 剛好一次的檢查失敗。帶 `\n` 的 `find` 在清單裡是跳脫過的，不會自我命中。

## 三、帳本（進版控，執行器跑完一條就寫）

`scripts/mutation-ledger.json`：`{ note, entries: { [突變名稱]: { last, lastFull } } }`

- `last`：最近一次（不論跑法）——日期、commit（工作區有改動加 `+dirty`）、跑法（`affected`／`full`／`never-full`／`only`）、怎麼結束（`kind`）、算不算數（`counted`）、紅了沒（`red`）、**紅的是不是預期那一種（`expectMatched`；沒寫 expect 的記 `null`）**、秒數、三個雜湊、範圍種類。
- `lastFull`：最近一次在**整套或補跑**（`full`、`never-full`）裡、**算數**的那一次。補跑也算：每條突變都是「改壞 → 跑一支測試 → 還原」，不帶狀態到下一條，在同一個 commit 上單獨跑跟在整套裡跑結果一樣。
- **只有算數的結束才記成紅或跑過**：逾時、被殺、沒跑起來 → `counted: false`、`red: false`、不寫 `lastFull`。（runkind 分清「斷言失敗」「崩潰」「逾時」「被殺」「沒跑起來」，見 `scripts/runkind.mjs`。）
- 寫檔用「寫暫存檔再 rename」，當機最多丟正在跑的那一條。
- 在 worktree 裡跑整套時，用環境變數 `MM_LEDGER=主 repo 的帳本路徑` 寫回主 repo（worktree 刪掉也不丟）。
- **初版從舊的「上次整套名單」轉入時**：沒有逐條證據的照實記（MealMate：442 條記成「09-24、那次的 commit、整套、紅」，`expectMatched` 不寫、雜湊留空 → 第一次 `--affected` 全部重跑）。**不要猜**。
- **孤兒檢查兩種都報**：清單有、帳本沒有（＝從沒跑過）；帳本有、清單已經沒有（突變被刪或改名）。
- **整套收齊才算跑完**（分段時用）：每一條在**同一個 commit** 上都有算數的結果、三個雜湊都是現在的。少一條、雜湊對不上、不算數的都不算。這是「分段＝一次跑完」的等價條件：同一 commit、雜湊認突變、每段先跑基準（這一段用到的測試沒有突變時全綠）、合起來剛好等於整份清單每條一次。

## 四、指令（MealMate 的介面，照抄時換成自己的）

| 指令 | 做什麼 |
|---|---|
| `npm run mutationtest` | 預設＝`--affected`（v11 §5.18） |
| `-- --full` | 整套；這個 commit 上已算數跑過、雜湊沒變的跳過（中斷後同一個指令就是續跑） |
| `-- --never-full` | 只跑從沒在整套（或補跑）裡跑過的 |
| `-- --only <關鍵字>` | 新防線當場證明會紅（§5.18 第 5 點） |
| `-- --limit N` | 這一次最多跑 N 條（分段） |
| `-- --dry-run` | 只列不跑：逐條列「會跑」（附理由）與「不跑」（附理由）；印依賴範圍的種類統計、整個 repo 的理由前 5 |
| `npm run sincefull -- --list` | 從沒整套跑過的逐條＋帳本孤兒 |
| `npm run sincefull -- --each` | 每一條上次整套的日期、commit、紅了沒 |

每次跑都印：選了幾條（共幾條）、跑法、受影響的理由統計、沿用幾條、選到的裡面幾條是整個 repo 以及為什麼。

## 五、對照組（每一條規則各一個樣本、各一條只紅它的突變）

**用記憶體裡的合成 repo**：一個 `{ 路徑: 內容 }` 的物件，`scopeFor(m, Object.keys(files), (f) => files[f])`。每條規則一個樣本，答案事先寫好：改了範圍裡的檔 → 雜湊要變；改了範圍外的 → 不變。**反方向也要一條**（「跳過真的會發生」：改了沒有任何關係的檔，雜湊不變）——否則「什麼都算進去」這種壞法不會紅。

樣本與突變的對照表見 MealMate STATUS「共用慣例副本更新到 v11」一節（§5.12 的格式：規則 → 樣本 → 只紅它的突變）。至少要有：只展開一層、讀不到當成沒有關係、每一種 import 寫法各漏認一次、未知類別當成不受影響、執行器改了不跑、上次不算數也沿用、帳本把平常跑法記成整套。

**真實入口**（§5.4）：在暫存目錄 `git init` 一個小 repo（複製 scripts/、放一支探針測試、把突變清單換成一條），連跑執行器：第一次要跑、帳本有紀錄 → 沒改東西時沿用、0 條要跑 → 改了探針間接 import 的檔時要跑、理由是「依賴範圍裡有檔案改了」→ 只改文件時沿用 → 加一條會卡住的突變、時限調成 3 秒，用 `--never-full` 跑：算數的那一條記成在整套裡跑過，逾時的那一條不算數、沒有 `lastFull`。

## 六、資源紀錄（v11 §5.19、§5.20）

`scripts/reslog.mjs --root <主程式 pid> --out <檔> --interval 60`：每 60 秒一行「時間、工作程序數、合計記憶體、系統可用記憶體」，主程式結束就停；`--once` 印一行就結束。

- **數法**：主程式的子孫裡，node／python 各算一個工作程序；瀏覽器實例算一個（`chrome` 的父程序不是 `chrome` 才算；它的子程序不另算個數、記憶體算）；git、shell、powershell 不算個數、記憶體算；記錄工具自己與它的子程序不算。
- Windows 取程序表：`powershell Get-CimInstance Win32_Process | Select ProcessId,ParentProcessId,Name,WorkingSetSize | ConvertTo-Json`；其他系統 `ps -eo pid=,ppid=,rss=,comm=`。取不到 → 那一行寫「取不到程序表」，不寫 0。
- **執行器裡怎麼接**：突變執行器是同步跑測試的（`execFileSync`），**不能在同一支程式裡 `setInterval`**——測試在跑的時候事件迴圈是卡住的。要另開一個子程序（`spawn`，不要 `detached`：主程式結束時一起收掉），結尾自己再記一行、收掉它、讀峰值。
- **證明真的記得到**：開一個只睡覺的假工作，記一行必須 ≥ 1；收掉之後記一行必須是 0（兩個方向）。合成的程序表驗數法（node 算、瀏覽器子程序不另算、git 不算、自己不算、別的主程式底下的不算）。突變：取程序數永遠回 0、瀏覽器子程序各算一個、把自己算進去、峰值取最後一行、取不到的行略過。
- **不要寫「加了上限所以不會再當機」**：2026-10-01 第一次當機另有 bugcheck `0x9F`。

## 七、改壞原始碼之前：先把原檔寫到磁碟，再加三道護欄（照抄時最先做）

**問題**：突變執行器直接改主工作區的原始碼、跑完靠 `finally` 寫回。程式被殺掉、當機、斷電時 `finally` 不會跑，壞檔就留在工作區（TripQuest 2026-10-02 查出來它的 `mutate.mjs` 是這樣；MealMate 10-01 兩次當機留下的壞檔是人工還原的）。**用「設一個旗標假裝中斷」驗不出這件事**——旗標那條路上 `finally` 照樣會跑。

**MealMate 的做法**（`scripts/mutationtest.mjs`）：
1. **改壞之前**，依序寫兩處紀錄：
   - 帳本的 `inflight`：「第 N 次開跑（`runSeq`）、哪一條突變、哪支檔、原檔的內容雜湊」，先寫、先存檔；
   - 磁碟上的還原紀錄 `scripts/.mutation-pending.json`：檔案路徑＋**原檔的完整內容**（不只雜湊，才還原得回去）。
   然後才寫改壞的版本。跑完（`finally`）寫回原檔、刪還原紀錄、清 `inflight`。
2. **下次啟動的第一件事**：有還原紀錄 → 照它寫回原檔、刪掉、印「上一次被中斷，已還原 某某檔」。
3. **兩處要一致**（Dispatch 2026-10-02：只有一份紀錄的話，它被刪掉就無從察覺）：
   - 還原那一步跑完，還原紀錄卻還在 → 拒絕（還原本身失敗）。
   - 還原的檔跟帳本記的不是同一支 → 拒絕。
   - 帳本記著未收尾、還原紀錄卻不在：比對那支檔現在的雜湊與帳本記的原檔雜湊——**不同 → 拒絕，指出第幾次開跑、哪支檔**；相同 → 照跑並註明（中斷剛好落在「刪掉還原紀錄」與「清帳本」之間時就是這樣，檔案沒事；一律拒絕會變成永遠關著的閘）。
4. **護欄一：開跑前工作區必須等於 HEAD**（`git status --porcelain`，執行器自己會寫的帳本與基準清單除外），不等就拒絕並列出檔案——上一次被殺掉留下的壞檔，不能被這一次當成原檔備份。`--only`（寫新斷言、還沒 commit 時用）例外，但要另外檢查：**目標檔已經含這條突變的「改壞後」字串、HEAD 那一版卻沒有 → 拒絕**。不是 git repo（檢查做不了）→ 拒絕。`--dry-run` 只列不改檔，照常列出、註明工作區有改動。加這一道之後，既有測試裡「在不是 git repo 的暫存複本跑執行器」的探針、以及「改了檔就直接再跑」的探針都要跟著改（先 `git init`＋commit、改完檔先 commit）——MealMate 的 doctest F1-11、F1-13、D18 各改了一處。
5. **一次只准一支改壞的檔**：要寫還原紀錄時發現它已經存在（上一支還沒收尾）→ 拒絕。「一次只改一支」是現在的結構，不是機制保證的；紀錄只記得一支，哪天變成一次動兩支，第二支會被靜默少記。

**驗法**（`scripts/resume-verify.mjs`，在暫存目錄 `git init` 的小 repo 裡，不碰主工作區）：
- **真的殺程序**：用 `--full` 開跑，等第一條記進帳本、第二條正在跑（改壞的檔在磁碟上、還原紀錄在）時 `SIGKILL`；先確認那支檔真的留在改壞的狀態，造不出來就判「造情境失敗」，不往下驗。
- **判定不信受測對象的自我陳述**：每支探針測試每跑一次就在 repo 外的標記檔寫一行（跑的是原樣還是改壞的版本），用它數每一條實際跑了幾次；還原看**內容雜湊**。
- 正常流程：還原（雜湊等於原樣）→ 續跑只跑沒跑完的、沒收齊點名缺的 → 再續跑收齊、總數等於母體。
- 對照組（複本裡故意弄壞，必須在**預期的那一關**報不符，抓在別關不算）：還原什麼都不做 → 卡在「還原」；續跑多跳一條 → 卡在「續跑第一段」。
- 每一道護欄各一個情境、**各有反向**（該照跑的照跑）：刪掉還原紀錄 → 拒絕、指出第幾次；人工還原後 → 照跑。工作區有改動 → `--full` 拒絕；`--only` 照跑。目標檔已是改壞後的樣子 → `--only` 拒絕。還原後不清紀錄的那一版 → 改第二支時拒絕。
- 守護欄的突變（`test: "resume-verify"`）兩個方向都有：拿掉拒絕（該擋的放行）、改成一律拒絕（該放的擋住）。
- 2026-10-02 第一版（沒有三道護欄時）實測：58 秒、同時最多 2 個工作程序；正常流程與兩個對照組全部符合。加了三道護欄後，8 條守護欄的突變在 `a62cb68` 上全部紅在預期那一條（1,665 秒、峰值 3 個）。

**「情境未成立」是獨立的結果類別，不能被算進「紅了」**（Dispatch 2026-10-02）：
- **同一條對照組一起跑和單獨跑結果不同，就是這道對照組不穩定的訊號，不是運氣問題。** MealMate 2026-10-02：8 條護欄突變一起跑時 2 條「紅錯地方」，同一條單獨跑卻紅對地方——原因是機器忙時殺程序錯過了時間窗，那一次「第二條跑到一半被殺」根本沒發生，結果紅在「造情境失敗」，被當成「紅了」。
- 「紅錯地方」與「情境未成立」意思相反：紅錯地方＝情境成立、被別條規則擋下（對照組不夠精準）；**情境未成立＝要測的狀況從頭到尾沒有發生，這次什麼都沒量到**。混在一起，一次沒有發生的測量就被記成一次測量。
- 拉寬時間窗只是治症狀。治法是讓「情境沒成立」無法偽裝成「情境成立且紅了」：
  - 判定取自**情境本身留下的痕跡**，不取執行器的推論，而且每一次都印出來（必留）：殺掉之後目標檔仍是改壞的內容、還原紀錄還在（兩者證明 `finally` 沒跑）、被殺的那支探針有「開始」標記、沒有「結束」標記（證明它跑到一半）。
  - 沒成立就換一個新的暫存 repo 再試，最多 3 次；還是沒成立，印一行以「⊘ 情境未成立」開頭的宣告、回傳值另外一個（MealMate 用 4）。
  - 執行器（`scripts/runkind.mjs`）看到那一行就判成 `noscenario`：**不算紅、不算通過、不算數**（列在 `UNCOUNTED_KINDS`），帳本不記成跑過，下一次選擇會再挑它。就算輸出裡也有 ✗、就算回 0，都照這樣判。宣告要在行首，說明文字裡提到那幾個字不算。
  - 對照組：故意讓殺程序一定錯過時間窗（探針不睡），必須判成「情境未成立」，不能判成紅、也不能判成綠。

## 八、上線順序（照抄時）

1. 先寫 depgraph 的純函式與合成樣本的對照組（輕量，隨時可跑）。
2. 執行器接上帳本與跑法；`--dry-run` 實跑一次（輕量）看分布——**先看「整個 repo」有幾條、理由是什麼**，那決定這套機制能省多少。
3. 帳本初版從舊紀錄轉入，沒有逐條證據的照實記。
