# SPEC_sincefull_按名稱計數 — 「從未整套跑過」改成按突變名稱比對

> 狀態：已執行（2026-09-19）
> 撰寫：Fable 5.1 統籌 Session，2026-09-19。另開新檔是因為你正在做第 2 件，統籌者不去動你手上的規格。只動 `scripts/` 與 docs，不 bump、不部署。

## 為什麼

你在 v0.36.1 回報的缺陷成立：`sincefull` 用條數相減（369 − 366 = 3），實際照名稱算是 5 條——刪掉的 2 條把差距抵掉了。條數相減是統籌者在修訂一 D3 的設計，**錯在設計，不在你的實作**：只要有刪突變或改名，這個數字就系統性偏低，而它偏低的方向正好是「讓人以為不急」。

## 要做的事

1. **基準清單落檔。** 新增 `scripts/mutation-lastfull.json`（要 commit）：`{ date, version, names: [...] }`，內容是上次整套實際跑過的突變名稱。這一次的基準從 git 取：`b98f271` 那一版 `scripts/mutationtest.mjs` 的 366 個名稱（用程式取，不要手抄）。
2. **`sincefull` 改算法。**「M 條從未整套跑過」＝現在的突變名稱裡，不在基準清單上的條數。改名的突變算沒跑過（保守，這是要的）。輸出照舊一行，M > 0 時後面不必列名稱；另加 `npm run sincefull -- --list` 列出那 M 條的名稱。
3. **整套跑完時更新基準。** `mutationtest` 不帶 `--only` 且完整跑完（沒有中斷、沒有漏跑）時，自動重寫 `mutation-lastfull.json`。中斷或帶 `--only` 時**不准寫**。分段補跑（像這次 309＋57）的情況：提供 `--record-full` 之類的明確開關由人確認後寫入，不要自動猜。
4. STATUS「上次突變整套」那行的條數留著（給人看），但 `sincefull` 不再拿它做減法；那行與 json 的 `date`、`version`、條數對不上 → `doctest` 紅。
5. 把 STATUS 裡記的那條「條數相減有誤差」的註記改成現在的事實。
