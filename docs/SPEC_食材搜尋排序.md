# SPEC：新增食譜找食材的排序（食物類別排在加工品前面）

> 狀態：**定稿（2026-10-01），待實作**。Yolin 2026-10-01：「那三件依你或統籌者建議的做」；Dispatch 交給開發 Session 判斷定稿。
> 草稿（2026-09-18）的「生鮮」說法改掉了，理由見下面「分界的依據」。

## 為什麼

新增食譜的食材框打「豬肉」，2026-09-18 實測前 8 筆是：
山豬肉片、冷凍豬肉湯圓、冷凍豬肉水餃、冷凍豬肉韭菜水餃、冷凍豬肉蟹黃水餃、冷凍豬肉熟水餃、冷凍豬肉餛飩、豬肉鍋貼。
「雞肉」「牛肉」也一樣，前幾筆多半是水餃、香腸、火腿、泡麵。
原因：`foods.searchFoods` 的順序是「精確命中 → 名稱包含 → 俗名包含」，名稱包含那一段照資料庫原本的順序。

## 分界的依據：食藥署的「食品分類」欄位，不看名稱

不用名稱的樣子去猜（「冷凍」「罐頭」開頭就算加工、「豬」字就算豬肉——這個系列一再踩過的坑：形狀不是分類）。
依據是每一筆食材在食藥署原始資料裡的 `食品分類`（`data/foods.json` 的 `cat`），三群：

| 群 | 食藥署分類 | 為什麼放這裡 |
|---|---|---|
| **食物類別**（排前面） | 穀物類、澱粉類、堅果及種子類、水果類、蔬菜類、藻類、菇類、豆類、肉類、魚貝類、蛋類、乳品類 | 食藥署按「這是什麼食物」分的類。同一類裡生的、乾的、熟的都有（白飯與米、乾香菇與香菇、皮蛋與雞蛋），所以**不叫「生鮮」**——那個詞會讓人以為這一群都是生的 |
| **未分類**（排中間） | 油脂類、糖類 | 精製過的原料（大豆油、冰糖），不是食物類別、食藥署也沒歸進加工品。分不出來的不硬塞一邊 |
| **加工品**（排後面） | 加工調理食品及其他類、糕餅點心類、調味料及香辛料類、飲料類 | 食藥署本身就分在加工、調製的類別 |

18 個分類每一個都要落在剛好一群；資料裡出現不在表上的新分類 → 歸「未分類」，並由測試點名（不默默歸哪一邊）。

## 要做的事（只動新增食譜畫面用的 `collapse: true` 那條路）

1. **先收齊、再排序、最後才取前 N 筆。** 現在的 `searchFoods` 是一邊走資料、一邊塞到 `limit`（20 筆）就停——只排「已經抓到的 20 筆」沒有用：資料庫順序在前面的加工品會先把名額塞滿，食物類別的根本進不來（共用慣例 §5.10：依筆數寫死的上限）。
2. 精確命中（別名、全名、俗名、簡名剛好等於打的字）永遠第一，不參與排序。
3. 「名稱包含」「俗名包含」兩段合在一起照群排：食物類別 → 未分類 → 加工品；同一群裡維持原本的順序（名稱包含在俗名包含前面、資料庫原順序）。
4. **畫面上看得出為什麼**：每一筆結果旁邊顯示它的食藥署分類名稱（「肉類」「加工調理食品」），結果清單上方一句「同樣命中時，食物類別排在加工品前面（依食藥署分類）」。不做分數、不做權重。
5. 不做同義詞擴充（打「豬肉」不會自動找「豬後腿肉」）：要擴充就加進 `data/aliases.json`，由 `aliastest` 守。不要用子字串猜（「豬」會撈到馬齒莧的俗名「豬母乳」，見 `foods.js` 開頭的註解）。
6. `collapse: false`（其他地方的搜尋）順序與筆數完全不變。

## 驗收（每一條新斷言都要突變驗紅）

- `unittest`：
  - 分群表：18 個分類各落在剛好一群；一個不在表上的假分類 → 未分類。
  - 搜「豬肉」「雞肉」「牛肉」：先斷言命中裡**同時有**食物類別與加工品（情境存在），再斷言所有食物類別的排在所有加工品前面。
  - **上限**：造一個假索引，前面 25 筆都是加工品、第 26 筆才是肉類，搜尋結果（limit 20）裡要看得到那筆肉類（修正前會紅）。
  - 未分類排在兩群中間；精確命中照舊第一。
  - 對照組：`collapse: false` 的結果與修正前逐筆一樣。
- `recipeviewtest`（真實入口）：新增食譜的食材框打「豬肉」，畫面上第一筆是肉類、旁邊顯示「肉類」，清單上方那句說明在。
- 既有的單一食材框測試全綠。
