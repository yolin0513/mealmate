> 建議 effort：跟原工單相同（medium）。

## 1. 定義改了什麼（取代原工單 §2 的對應條文；其餘不變）

1. **本機絕對路徑分三級**（取代原 §2「算」第 4 類裡的「本機使用者名稱、本機絕對路徑」）：
   - **含使用者名稱或家目錄的路徑 → 算個資**（照原第 4 類回報）。
   - **只有磁碟機代號加專案路徑、不含使用者名稱 → 不算個資**，改列進新的「清理建議」表（見 §2）。共用慣例 v5 §2.4 本來就不准再新寫進 repo，但那是 repo 的衛生，不是個資；清不清、怎麼清另外決定。
   - **每台電腦都一樣的系統路徑**（例如 Windows 系統字型的位置）→ 不算，也不必列：它指不到任何人，也不是這台機器特有的。
2. **使用紀錄限定「Yolin 或家人的真實紀錄」**（改寫原 §2「算」第 5 類）：開發或測試時為了重現問題自己跑出來的數字（例如「連做 200 題全對」、測試腳本寫進去的作答數）不算。
3. **已經寫在公開 commit 作者欄的帳號名稱不算**（補進原 §2「不算」）：它本來就顯示在每一個公開的 commit 上，只改檔案拿不掉——跟 GitHub 帳號 `yolin0513` 不算是同一個理由；改名前的舊帳號名稱也一樣。

## 2. 回報格式（改寫原工單 §6 第 2 點）

- 「個資清單」只放照新定義算個資的。
- **新增「清理建議」表**：不算個資、但照 v5 §2.4 不該留在 repo 的東西——檔案｜行號（二進位檔寫檔名）｜是什麼（只寫類型，不貼值）｜建議怎麼清。
- **二進位檔裡帶的路徑也要查**：例如 `__pycache__` 底下的 `.pyc`，編譯時會把原始碼的完整路徑寫進去，文字掃描看不到（JLPT_App 就是另外查到的）。其他編譯產物、壓縮檔同理。
- **「從 repo 移除已 commit 的檔」（例如 `git rm --cached`）屬於刪除已 commit 的檔：只寫建議，不要做**，要不要做由 Yolin 決定。

## 3. 重申（原工單 §5、§7 已寫，JLPT_App 照做了，請比照）

普查結果只寫在回報裡；repo 只記一行「個資普查已回報（日期），結果不進 repo」。把「個資在哪一行」的清單寫進 repo，等於把個資再抄一份、還附上地圖。
