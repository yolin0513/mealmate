# SPEC_高蛋白食材的輪替群組 — 麵腸、麵筋這類份量夠的高蛋白食材，也算一種「蛋白質來源」參加主菜輪替

> 狀態：**已執行（2026-09-23、v0.41.0）**
> 規劃：Fable 5.1 統籌 Session，2026-09-21。**本檔推翻統籌者同一天稍早的決定「不給麵腸／麵筋輪替群組」**——那是統籌者自己判斷的，Yolin 之後裁示了（§6）。另開新檔是因為你的工作區有未提交的變更。

## 一句話

一道菜裡有「每 100 克蛋白質 ≥ 14、而且每份吃到 ≥ 6 克」的食材（v0.39.0 那條路的同一個判準、同兩個常數），這道菜的 `proteins` 就多一個群組 `highprotein`，主菜的蛋白質輪替照常對它作用。**這個群組與 `soy` 分開。**

## 1. 設計原則（請寫進你的 STATUS，往後同類問題不必再逐案問）

**Yolin 的一貫原則：看含量，不看名稱或分類。** 他已經三次用同一個邏輯裁示——豆芽（2026-09-19「如果他們的蛋白質含量很高也可以排菜」）、麵腸（09-21「麵腸等高蛋白質食材也算」）、麵筋（09-21「麵筋如果蛋白質高也可以列入」）。往後遇到「某樣食材算不算○○」：先問能不能用含量訂門檻，不要用名稱清單。

## 2. 現況（統籌者 2026-09-21 唯讀實查，行號以你讀到的為準）

- 蛋白質輪替只作用在主菜（`planner.js` 約 604–614 行）：這道主菜的 `recipe.proteins` 裡有群組當天已經出現過 → −25；前一天同一餐出現過 → −8；理由句「蛋白質來源：○○」用 `PROTEIN_LABELS`。「當天出現過」統計的是那一天**所有角色**的菜的 `proteins`（約 815 行）。
- `recipe.proteins` 由 `recipeschema.validateRecipe` 逐樣食材呼叫 `proteinGroupOf(food, tags)` 推出來——**只看食材是什麼，不看用了幾克**。
- 紅燒麵腸現在 `proteins` 是空的：輪替上它「沒有蛋白質來源」，同一天排兩道麵腸／麵筋的菜不會被扣分。
- v0.39.0 的判準（`planner.js`）：`HIGH_PROTEIN_PER_100G = 14`、`HIGH_PROTEIN_PER_SERVING = 6`、排除穀物類／澱粉類與帶肉或海鮮標籤的食材。

## 3. 決定與理由

1. **誰算進這個群組：沿用 v0.39.0 的同一個判準與同兩個常數，不另訂門檻。** 兩條規則問的問題不同（達標問「這一餐有沒有蛋白質來源」、輪替問「是不是又同一種」），但「這樣食材在這道菜裡算不算蛋白質來源」是同一個事實，只該有一個定義。另訂一組門檻，會出現「算達標卻不算來源」或反過來的菜，沒有人解釋得清楚。
2. **一定要看每份克數，不能只看每 100 克。** 只看含量的話，乾香菇（20.9）、芝麻、花生碎這種撒幾克的配料會把一大堆菜都標成同一個群組，輪替就亂了。所以這個群組**不能做在 `proteinGroupOf` 裡**（它拿不到克數與份數），要做在 `validateRecipe` 逐樣食材那一段：這樣食材沒有既有群組、而且符合高蛋白判準（份數的取法與 `proteinDishMatch` 一致：共用那一欄除以 `servings`，素／葷那一欄除以各自的份數）→ `proteins`（以及對應的 `vegProteins`／`meatProteins`）加 `highprotein`。
3. **與 `soy` 分開，不併。** 輪替要攔的是「同一種來源連著吃」。麵腸是小麥、豆腐是黃豆，同一天各一道不是重複，不該扣分；同一天兩道麵腸／麵筋才是。併進 `soy` 的話，全素家庭本來就偏緊的主菜池會再被多扣一層。代價：素肉、素雞塊的原料其實是黃豆，卻會落在 `highprotein`——它們不叫豆腐豆干、名稱規則認不出來；這是「看含量不看名稱」的自然結果，接受。
4. **判準只定義一次。** 把 v0.39.0 那個判斷（含兩個常數與排除條件）搬到 `recipeschema.js` 匯出，`planner.js` 改成引用；不要兩邊各寫一份。`planner.js` 既有的匯出名稱保留（重新匯出即可），不要讓既有測試與突變的 `find` 大面積過期。
5. **理由句**：`PROTEIN_LABELS` 給 `highprotein` 一個使用者看得懂的字。統籌者建議「麵腸、麵筋這類」太長；用 **「高蛋白素料」** 或你認為更自然的兩到五個字，過 `copytest`，寫進回報。

## 4. 規則

- **R1** `validateRecipe`：食材沒有既有群組（`proteinGroupOf` 回 null）、符合高蛋白判準 → 加 `highprotein`。有既有群組的（豆干 19.3 也符合含量）照舊只有原群組，不重複加。
- **R2** 判準搬家（§3.4）。v0.39.0 的達標判定結果一道都不變。
- **R3** `PROTEIN_LABELS.highprotein`。
- **R4** 重建 `recipes.json`：預期只有紅燒麵腸、以及配菜那一版新增的麵腸／麵筋菜的 `proteins` 會變。**實際變動的清單逐道列進回報；出現預期外的菜（尤其是菇、堅果、主食類）就停下來回報。**
- **R5** 使用者自己的食譜走同一段程式，自然適用；已經存著的要等他下次編輯存檔才重算（同 v0.38.0 的 R8），不做遷移。
- **R6** 統計門檻：這一版會改主菜的排法。`plannertest` 三種家庭的「排不到」比例、「同一樣主角三天內」、`soy3` 那幾條，改動前後並列回報；門檻只在實測需要時照補遺第 12 條調，並說明。
