### 1.3 食材名稱對應：這是要另外做工的地方【實測】

用家庭常用叫法去搜「樣品名稱＋俗名」：

| 搜尋 | 命中 | 說明 |
|---|---|---|
| 白米 | **0** | 資料庫叫「白飯」「糙稉米(台稉71號)」等，沒有「白米」二字 |
| 無糖豆漿 | **0**（「豆漿(無糖)」才 1 筆） | 括號寫法對不上口語 |
| 雞蛋 | 25 筆，多是「雞蛋豆漿」「雞蛋麵」「雞蛋豆腐」 | 全蛋要找「雞蛋白平均值」「雞蛋黃平均值」或白殼／紅殼雞蛋條目 |
| 高麗菜 | 11 筆，正式名「甘藍」，俗名欄才有「高麗菜」 | 俗名欄很有用，但要用「精確詞」比對，不能用子字串 |
| 豬 | 83 筆，前幾筆是「馬齒莧（俗名豬母乳）」「野莧菜（豬莧）」 | 子字串搜尋會嚴重誤判 |
| 雞 | 118 筆，含「鷹嘴豆」「雞絲麵」「乾木耳(黑耳仔)」 | 同上 |
| 豬絞肉 | 4 筆：豬絞肉(90％瘦肉率)／平均值／(70％瘦肉率)、雞絞肉 | 有「平均值」條目可當預設 |
| 傳統豆腐、味噌、秋刀魚、燕麥、洋蔥、空心菜、木耳、南瓜 | 1–10 筆，可用 | 正常 |

**結論**：食譜資料不能靠「食材名稱字串」去查營養，要在轉檔時做一張**食材別名表**（`白米→糙稉米或白飯`、`高麗菜→甘藍`、`蛋→雞蛋平均值`…），每道食譜的每個食材直接存**整合編號**。這張表是開發期 M0 的工作，而且要有測試：**每道食譜的每個食材都必須解析到一個存在的整合編號，否則測試紅**。

### 1.4 精簡後的體積【實測】

把 2,180 種食材只留 12 項關鍵營養素、名稱、分類，寫成 JSON：**353,969 bytes（354KB）**。範例：

```json
{"id":"A0550601","name":"白飯","cat":"穀物類","n":{"粗脂肪":0.3,"粗蛋白":3.1,"鈣":1,"鈉":2,"鉀":40,"飽和脂肪":0.1,"熱量":183,"糖質總量":0,"膳食纖維":0.6,"磷":39,"總碳水化合物":41,"膽固醇":0}}
```

若只帶「食譜用到的＋常見採買食材」（估 400–600 種）會在 100KB 以內，gzip 後更小。**離線可行，不需要後端**。

### 1.5 「每道菜預標」還是「食材累加」？【推論，建議累加】

| 方式 | 優點 | 缺點 |
|---|---|---|
| 每道菜預先標一組數字 | 簡單 | 使用者改份量、換食材、手動加菜就沒數字；沒有來源可追 |
| **食材克數 × 每 100 克含量累加** | 手動加菜自動有標示；改份量自動重算；可追到食藥署條目；素／葷分流各算各的 | 需要每個食材有克數；烹調損耗（吸油、水分蒸發）不會反映 → 一定要標「估計值」 |

採累加。**鈉的主要來源是調味料**（醬油、鹽、味噌、蠔油），所以食譜的食材表必須把調味料也列進去並給克數（1 小匙鹽 ≈ 6 克、1 大匙醬油 ≈ 15 克 —— 這些是常識換算，開發期寫進換算表並標示為近似）。這是「附營養標示」能不能對長輩有意義的關鍵。

### 1.6 備援：USDA FoodData Central【推論，未實測】

搜尋結果：資料為 CC0（公有領域）、需免費 api.data.gov 金鑰、每小時 1,000 次／IP。**不建議用**：英文名、美式食材、要打外部 API。食藥署資料已足夠，USDA 只當「食藥署沒有的西式食材」的手動查表來源，不進 App。

### 2.2 食譜的著作權界線【依智慧財產局說明推論】

著作權法第 10 條之 1：保護「僅及於該著作之表達，而不及於其所表達之思想、程序、製程、系統、操作方法、概念、原理、發現」。

- **食材清單、用量、烹調程序本身**：屬程序／方法／事實，**不受保護**。
- **步驟的文字寫法、照片、排版、故事文案**：是表達，**受保護**。

所以做法是：**菜名與食材組合可以參考任何來源，但步驟文字一律自撰、不用任何網站的照片、不抄任何段落**。國健署手冊的文字若確認在開放宣告範圍內，可在標示來源下改作；圖片不用。

### 2.3 要多少道菜才撐得起「每週儘量不重複」【推論，數學而已】

設定：一週 21 餐；早餐在真實家庭多半輪替少數幾樣（稀飯配菜、吐司蛋、燕麥），**建議早餐不納入嚴格不重複**，只做 7–10 種輪替。午、晚各 7 餐 ＝ 14 餐，每餐 1 主菜 ＋ 1–2 配菜 ＋ 湯（選）。

| 目標 | 需要的主菜數 | 配菜數 | 湯 |
|---|---|---|---|
| 一週內主菜不重複 | ≥ 14 | ≥ 14（若配菜也不重複；建議配菜允許一週內出現 2 次 → ≥ 8） | ≥ 4 |
| 兩週內主菜不重複 | ≥ 28 | ≥ 16 | ≥ 7 |
| 四週內主菜不重複 | ≥ 56 | ≥ 28 | ≥ 14 |

但**篩選會縮小池子**：家中有蛋奶素成員 → 只剩「本身是素」或「可分流」的菜；有糖尿病長輩 → 高醣主食型主菜（炒飯、炒麵、勾芡濃羹）排序後移；季節不對的菜再扣一些。經驗上篩完剩 50–60%。

**建議 v1 規模：主菜 80、配菜 50、湯 25、早餐 10、主食 6（白飯、糙米飯、雜糧飯、地瓜、麵、粥）→ 約 170 道。** 這樣有素食成員時仍有 40 道以上主菜可排，做到「兩週不重複、四週儘量不重複」。演算法要在池子不夠時**誠實顯示**「本週有 N 道是兩週內重複，因為符合條件的菜只有 M 道」，而不是硬塞。

### 2.4 自建的人力估計與維護方式【推論】

- 每道菜要寫：菜名、分類、份數、食材（整合編號＋克數＋採買單位）、步驟（自撰、3–8 步）、可否分流與分流點、標籤（葷素、五辛、蛋、奶、海鮮、堅果、質地、季節、烹調時間、烹法）。
- 170 道 × 每道約 10–15 分鐘（含查食藥署編號）＝ **30–40 小時**。這是 Opus 開發期最大的單項成本，可以用 AI 起草＋人工檢查，但**每道都要過「食材編號解析」「克數皆 > 0」「步驟數 ≥ 3」「分流菜必有 base／veg／meat 三段」的自動測試**。
- 維護：每道一個 JSON 檔放 `data/recipes/`，`scripts/build-recipes.mjs` 合併成一個 `data/recipes.json` 並跑 schema 驗證；使用者手動新增的食譜用**同一個 schema** 存 IndexedDB。

## 4. 純前端 PWA 的技術可行性【推論，沿用既有三個 App 的實證】

| 項目 | 結論 |
|---|---|
| 資料量 | 食材 100–350KB ＋ 食譜 170 道約 200–300KB（無圖）→ 首載 < 1MB，SW 快取後離線全功能 |
| 圖片 | **v1 不放菜色照片**（版權＋體積＋沒有來源）。用分類插圖或 emoji 圖示即可，明亮時尚靠排版與色彩 |
| 儲存 | IndexedDB；請求 `navigator.storage.persist()` 避免被瀏覽器清掉；匯出／匯入 JSON 備份沿用 StockDiary 做法 |
| 外部請求 | **零**。CSP `connect-src 'self'`；沒有任何網路呼叫，也就沒有隱私外洩面 |
| 演算法 | 週計畫產生是純函式（輸入：食譜池、家人設定、歷史、買菜日、種子；輸出：21 個格子）→ 可用固定種子做確定性測試與突變測試 |
| AI | v1 不用。若日後要「用 AI 起草手動食譜」，比照 TripQuest：自備金鑰、瀏覽器直連、獨立 store、永不匯出；成本以美分計 |

## 5. 這次沒驗證到、開發期要補的

1. 國健署與健康九九的頁面實際內容與開放宣告全文（curl 403、WebFetch 憑證失敗）。
2. 食藥署 JSON 裡「值為空」的比例（這次只驗了欄位存在，沒驗每個值非 null）。
3. 食材別名表要涵蓋多少個口語詞才夠（等食譜寫出來才知道）。
4. 採買單位換算（一把、一顆、一斤、一盒）的常識表——沒有開放資料，要自建並標「近似」。
5. 食材保存天數表（葉菜 3 天、根莖 7 天、冷藏肉 2 天…）——常識，要標「可自行調整」。
