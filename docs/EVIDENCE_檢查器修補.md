### 驗法

指令：`node --max-old-space-size=4096 scripts/buildguard-verify.mjs --rev <commit>`。
- 在 repo 外的拋棄式 worktree 跑，原始資料用複本。
- 母體＝每一個單位 × 每一種情境，寫成迴圈。
- 一格要四件事都成立才算擋：
  1. 回傳非 0。
  2. **錯誤訊息的位置**（stderr 從「✗」那一行起）點名這個單位。食譜 id 要對邊界，`r-foo` 不能被 `r-foo-veg` 湊到。
  3. 輸出檔雜湊沒變，也沒留下暫存檔。
  4. 沒有吐出未處理例外的堆疊。
- 回非 0 但沒點名，算碰巧擋下，也就是算沒擋。
- 跑矩陣之前先跑判準的對照組，兩個方向共 10 種：只出現在正常進度訊息裡要判「不算」，出現在錯誤訊息裡要判「算」；還有前後綴湊到、只有堆疊沒有「✗」、比對模式的擷取。對照組不對就不往下跑。
- 兩份結果比對前，先用 `--compare <舊 log> <新 log>` 斷言兩邊每一組抽到的格數相同而且大於 0。
- 每一組也對預期數量：食譜檔數要等於那個版本 `recipes.json` 的道數；類別數要每一個都在原始資料裡找得到。

## F9：驗法登記制，四家統一（2026-09-24，統籌者訂；Dispatch 轉達）

**統籌者補的兩點，本 App 的做法**
1. **登記的是被守的檔「已 commit 版本」的雜湊**；登記前先斷言工作區那三支跟 HEAD 一模一樣，有改動就不登記。
   `buildguard-verify` 開跑前就先講「跑完不會登記」，跑完登記前再查一次；途中 HEAD 動了也不登記。
   只有 `--rev` 是 HEAD、全跑（沒有 `--only`）、全擋才登記；HEAD 沒全擋會刪掉登記。
2. **第零關之二只在「這次要推的 commit 動到被守的檔」時才看登記**。
   - 範圍照遠端的實際狀態算：放在 fetch 之後，取 `origin/main..HEAD`。
   - 逐個 commit 取檔名：中途改了又改回去的也算動到；取不到檔名清單就回 5。
   - 動到了才比 HEAD 裡的雜湊，比的不是工作區。
   - **例外**：推送閘本身那三支（閘門、自查、閘門驗法）是第零關，照舊一律要先驗，新 clone 也一樣。

**三段證據**

1. **舊版真的是舊的**：`307fced`（F8 登記制的第一版）有三個問題。
   - 第零關之二放在 fetch 之前、不看範圍：只要沒有登記就回 5，所以新 clone 一律要先跑 7 分鐘。
   - 比的是工作區的 `hash-object`，不是已 commit 版本。
   F9 在 `51d0739` 起改，閘門驗法的第 19 種在 `2b8a3eb` 補上。
2. **舊的寫法會漏的，逐一造出來**：在拋棄式 worktree 把 `2b8a3eb` 的閘門改回舊寫法、commit 後跑閘門驗法。每一條只紅在預期的那一種，對照組（原樣）19 種全部符合。
   - 「不管有沒有動到都看登記」（新 clone 一律要先跑）：只有第 17 種不符合（回 5，預期 0）。
   - 「比工作區、不比已 commit 版本」：只有第 18 種不符合（回 5，預期 0）。
   - 「只看最後一個 commit 的檔名」：只有第 19 種不符合（回 0，預期 5）。這是我這次多補的一種：動到 build 的是前一個 commit、最後一個 commit 是乾淨的。
3. **新版全符合**：閘門驗法共 19 種，預設順序與反向順序都全部符合。
   - 第 15 種：commit 動到 build、登記對不上 → 回 5。
   - 第 16 種：commit 動到 build、沒有登記檔 → 回 5。
   - 第 17 種：新 clone 沒有登記、推的 commit 沒碰被守的檔 → 照推。
   - 第 18 種：登記的是已 commit 版本，工作區另有沒 commit 的改動 → 照推。
   - 第 19 種：前一個 commit 動到 build、最後一個乾淨 → 回 5。

**常設**
- doctest F8-9 驗登記的判斷：不是 HEAD、`--only` 不登記、不動現有登記；HEAD 沒全擋、途中 HEAD 動了、工作區不乾淨，都刪掉登記。
- 突變「登記不管是不是 HEAD」「登記不管工作區乾不乾淨」用 `--only` 跑，都紅在指定的斷言。
- gatescan 登記一條例外：閘門用 `git log --format= --name-only` 取的是檔名清單，不是新增行，所以不適用「用 --format= 取新增行卻沒取訊息與作者欄」那條規則。

### F9 補：工作區有改動時的常設情境（2026-09-24，Dispatch 轉達統籌者在 JLPT 查到的缺口）

**缺口**：把「工作區跟 HEAD 不一樣就不登記」那一段改成一律當成沒改動，閘門驗法 19 種照樣全部符合。驗的是工作區、登記的是 HEAD，等於 HEAD 那一版沒被驗過卻被登記成驗過。本 App 原本只有純函式的 F8-9 守「判斷」，守不到「算出有沒有改動」那一步。

**改法**
- 工作區有改動、或跑的途中 HEAD 動了：不登記，**舊登記也刪掉**。前一版是「不登記、不動舊登記」，照 Dispatch 的兩種情境改回刪掉。
- 跑完之後的登記抽成 `finalizeRegistration`，驗法本身就走這一步。
- 新增 doctest **F8-10**（每版跑），從 `finalizeRegistration` 進來，在暫時的 git repo 造兩種情況：
  - 對照：工作區跟 HEAD 一樣 → 登記。登記內容用 `git ls-tree` 另外算來比，不拿登記程式自己用的 `rev-parse` 跟自己比。
  - 前提：舊登記在，而且工作區的 build-foods 跟 HEAD 裡的 blob 不一樣。
  - 斷言：跑完 → 沒有登記、舊登記被刪。

**突變只紅這一種**：在拋棄式 worktree 把 `dirtyGuarded` 改成一律回空、commit 後跑。
- doctest 只紅 **1 條**，就是 F8-10（「register｜HEAD 全擋…」）。
- 閘門驗法 19 種全部符合，重現了統籌者在 JLPT 看到的缺口：閘門的情境本來就看不到這一段。
- 對照（原樣）：doctest 0 紅、閘門驗法 19 種全部符合。
- 這條已登記成常設突變「buildguard 工作區有改動一律當成沒改動」，用 `--only` 跑，紅在 F8-10。

**第 2 種情境（沒動到被守的檔就不看登記）**：本 App 有專用的第 17 種（新 clone 沒有登記、推的 commit 沒碰被守的檔 → 照推），另外有突變證明只紅它。

**「A 跟 B 一樣」要先證明是兩個不同來源**：`--compare` 原本同一份 log 比兩次也會印「母體相同」。現在兩份 log 的版本要不同，否則判失敗。
- doctest F8-11 驗兩個方向：同一份比兩次判失敗、不同版本通過。
- 突變（拿掉版本檢查）紅在 F8-11。

**閘門突變收進 repo**：`scripts/gatemutants.mjs` 共 5 條（對照、拿掉第零關之二、F9 的三種舊寫法），每一條不符合的要恰好是預期那幾種。在 `9b8854d` 跑：5 條全部如預期。擷取本身先跑對照組，抓空就停。

## F10：失敗路徑的統一做法（2026-09-24，統籌者訂；Dispatch 轉達）

**做法**
- shell：在 PATH 最前面放一個假 git，只讓指定的子指令失敗，其他照常交給真的 git。假 git 本身要有對照組。
- JS：外部依賴從參數進來。
- 不在正式程式裡留「設了某個變數就故意失敗」的後門。
- 每個失敗分支要有一種情境，並做一次突變；被後面另一道接住、理由不對，也算紅。

**1. 拿掉後門**
- 我上一輪在閘門驗法留了 `PUSHGATE_VERIFY_S11_RANGE`，正是 F10 不准的後門。已拿掉。
- 第 11 種的「取不到 diff」改由 `gatemutants.mjs` 用假 git 觸發：只讓同時帶 `-p --no-color -U0` 的 `git log` 失敗。

**2. 假 git 的對照組**（兩處都做）
- 每次用假 git 之前先驗三項：
  - 指定的子指令必須失敗，而且是假 git 故意的；
  - 不相干的 `git rev-parse` 必須照常；
  - 同一個 `log` 子指令、不帶那些旗標必須照常。
- 閘門驗法第 20 種的前提也照這三項改了。
- `gatemutants.mjs` 開跑前另外驗兩個方向：
  - 好的假 git 三項都過；
  - 太粗的假 git（整個 `log` 都失敗）要被第三項抓到。
  兩個方向都對才往下跑，不然只證明了「把 git 弄壞就會停」。

**3. 每個失敗分支：情境＋突變，只紅那一種**

| 失敗分支 | 情境 | 突變（拿掉那個「停」） |
|---|---|---|
| 閘門：取不到檔名清單 → 回 5 | 閘門驗法第 20 種（假 git 讓 `--name-only` 失敗） | 只有第 20 種不符合 |
| 閘門驗法：取不到 diff → 明講 | `gatemutants`「失敗路徑」那一條：只有第 11 種不符合、理由是那一句 | 第 11 種照樣不符合，但理由變成「前置不成立」，被後面接住、理由不對，算紅；判準用 `must`／`mustNot` 比對理由 |
| 登記：讀不到雜湊 → 刪登記 | doctest F8-12：給一個不是 git repo 的資料夾（git 從參數進來，自然失敗），先斷言 git 真的失敗、舊登記在 | 改成留著舊登記 → 只紅 F8-12 |

**4. 排進下一輪的兩件，一起做了**
- `gatemutants.mjs` 可以指定改哪一支檔、用哪個驗法跑（閘門驗法或 gatescan），M4、M6 都收進來了。
  - M6：`fresh` 不清 hook → 預設順序第 6、7、12、17、18 種不符合。
  - M4：第 11 種前置斷言改回接管線 → gatescan 只點名那一行。
- F8 矩陣「輸出檔沒動」的合成對照格：每次跑矩陣之前，先用兩支合成的 build 跑，都印出設計好的理由、回 1。
  - 失敗時仍寫出一個位元組的那支：要判「沒擋」，而且是「輸出檔沒動」這一項抓到的。
  - 不寫的那支：要判「擋」。
  - 突變：「輸出檔沒動」永遠成立（暫存區的複本）→ 第一個方向判錯，驗法停下，沒有往下跑矩陣。

**結果**

## 正式閘門不讀測試用環境變數（2026-09-25，v10 候選；Yolin 核准先做）

**找到的實例**：`pushgate.sh` 讀 `PUSHGATE_REMOTE`，整個 repo 沒有任何地方用到它，是早期留下的旋鈕。設了它，fetch、自查的範圍、推送會一起改指到別的遠端：閘門對著另一個遠端做完整套檢查，然後說通過。

**處置：直接移除**，`REMOTE` 固定成 `origin`。
- 移除不影響任何東西：閘門驗法用 `git remote set-url` 換遠端，沒靠它；`gatemutants` 以 `$REMOTE` 當錨點的突變照樣對得上。
- 移掉之後就不需要靠白名單守它。

**gatescan 新規則**：TARGETS 裡讀了、卻沒在同一支檔裡賦值、也沒登記在 `ENV_ALLOW` 的環境變數，一律報出來。
- 白名單四條，各寫了理由：自查的 `USERNAME`、`USER`；閘門驗法的 `PATH`（假 git）、`PUSHGATE_VERIFY_ORDER`（只改順序、不改判準）。
- 登記了卻沒用到，也算失敗。
- **寫的時候自己的對照組抓到一個洞**：`X="${X:-預設}"` 這種賦值時讀自己的寫法，會被當成「已賦值」而躲過去，換這個寫法 `PUSHGATE_REMOTE` 就溜掉了。已改成「賦值那一行自己讀自己也算讀環境變數」，並加成對照樣本。
- 對照組共 5 種、兩個方向：要抓到的兩種 shell 寫法和 JS 的 `process.env`；賦值過的、註解裡的不能誤報。
